# Terraform AKP Provider Version 0.17 Upgrade Guide

Version 0.17.0 changes how the provider installs agent manifests and how custom-size cluster state is stored. This guide covers the upgrade from version 0.16.x to version 0.17.0.

Upgrading does not require resource renames or configuration changes. The only state change, for custom-size clusters, is migrated automatically during refresh. Terraform CLI 1.11.0 or later remains required. If you are upgrading from an older provider version, also follow the [v0.16 upgrade guide](v0.16-upgrading.md).

## Provider Version Configuration

Before upgrading, run `terraform plan` with your current provider version and resolve any unexpected changes. Back up your configuration and state, then update the provider version constraint:

```terraform
terraform {
  required_version = ">= 1.11.0"

  required_providers {
    akp = {
      source  = "akuity/akp"
      version = "~> 0.17.0"
    }
  }
}
```

Run `terraform init -upgrade` to install the new provider, then review `terraform plan`.

## Agent Manifest Installation

`akp_cluster` and `akp_kargo_agent` install agent manifests with Kubernetes server-side apply instead of client-side apply. The provider owns the applied fields under the field manager `terraform-provider-akp` and takes over conflicting fields held by other managers.

Manifests are applied on create, and on update only when `reapply_manifests_on_update = true`. Upgrading the provider alone does not touch the cluster. The first manifest apply after the upgrade migrates ownership of objects installed by an earlier provider version and prunes fields that are no longer part of the generated manifests.

Server-side apply validates manifests against the target cluster's API schema. Fields the cluster does not know are rejected by the API server instead of being silently dropped. Install an agent version that is compatible with the target cluster.

When `remove_agent_resources_on_destroy = true`, destroy waits up to ten minutes for each object rather than indefinitely. Destroying an `akp_kargo_agent` then fails, so remove the blocking finalizer and run `terraform destroy` again. Destroying an `akp_cluster` reports the failure in the logs and still removes the cluster from the Akuity API, so any object that was not deleted stays in the target cluster and has to be removed by hand.

## Custom-Size Cluster State

Previously, an `akp_cluster` with `custom_agent_size_config` configured and
`kustomization` omitted stored the generated resource patches in
`spec.data.kustomization`. On subsequent updates, those patches could be treated
as user input and rejected as conflicting with `custom_agent_size_config`.

Version 0.17 keeps generated sizing patches out of this resource attribute.
Existing state containing only generated patches is migrated to null during
refresh. This does not remove the custom resource settings from the agent or
require recreating the cluster. When `kustomization` is omitted and there are no
other changes, the migration does not require an API update. Nonconflicting
user-supplied kustomizations remain in resource state.

### Expressions That Read the Resource Attribute

Expressions or scripts reading `akp_cluster.example.spec.data.kustomization`
must allow null. If they need the API's generated kustomization, read the
`akp_cluster` data source instead:

```terraform
data "akp_cluster" "example" {
  instance_id = akp_cluster.example.instance_id
  name        = akp_cluster.example.name
}

output "generated_kustomization" {
  value = data.akp_cluster.example.spec.data.kustomization
}
```

### Redundant Patches in Configuration

Do not copy the generated resource patches into `kustomization` alongside
`custom_agent_size_config`. Such redundant configuration could previously have
an empty plan while failing on updates. After upgrading, it can produce a plan
diff and an apply error even without another configuration change:

```text
kustomization contains resource patches for argocd-application-controller,
which conflicts with custom_agent_size_config
```

Remove the redundant resource patches, or omit `kustomization` if it contains
only those patches. Keep `custom_agent_size_config` and any unrelated user
customizations, then run `terraform plan` again and apply the reviewed changes.

## Apply the Change

After updating the provider version, run:

```shell
terraform init -upgrade
terraform plan
```

Review the plan before applying it. A custom-size cluster whose state still holds generated patches shows `kustomization` changing to null; that change is the migration described above and does not modify the agent.
